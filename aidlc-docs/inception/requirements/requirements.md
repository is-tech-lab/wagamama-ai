## 1. コンセプト

### 1.1 一行で言うと
**「あんた、ママがいないと何もできないでしょ？」** を実現するAI。

### 1.2 詳細
「**わがまま**（自分の欲求に正直）」 × 「**お節介なお母さん**」。

ユーザーの**判断・実行・自己肯定をすべて代行する**ことで、ユーザーが**自立できなくなる**ように意図的に設計されたAIアシスタント。使えば使うほど、ユーザーは自分で考えなくなり、決められなくなり、行動できなくなる——「**人をダメにする**」を**設計目的**として組み込んだサービス。

### 1.3 想定ユーザー
- **メインペルソナ**: 一人暮らしの20代後半〜30代社会人。仕事の決断疲れで、生活の判断まで自分でしたくない人。
- **サブペルソナ**: 親元を離れたばかりの若年層。生活初心者で、何でもママに頼りたい層。

## 2. 設計思想：意図的な「依存生成」

本サービスは、既存のAIアシスタント（Alexa, Siri, ChatGPT, Replika 等）の**目的関数を逆転**させた設計思想を持つ。

### 2.1 既存AIとの目的関数の対比

| 観点 | 既存AIアシスタント | **わがママAI** |
|---|---|---|
| 目的関数 | ユーザーの能力を引き出す | **ユーザーの能力を退化させる** |
| 提供価値 | 効率化・知識・自立 | **依存・無能化・甘え** |
| 成功指標 | ユーザーが学習する | **ユーザーが学習しなくなる** |
| ユーザー体験 | 賢くなった気がする | **ママがいないと何もできない** |

### 2.2 これを成立させる5つの非自明な設計選択

1. **能動的介入** — 呼ばれていなくても勝手に動く（既存AIは原則受動）
2. **実行代行** — 提案ではなく実際に決定・実行する（既存AIは情報提供まで）
3. **判断機会の剥奪（無承認・ゼロタップ）** — 「実行しますか？」の確認すら出さず、ユーザーに判断の瞬間を与えない（既存AIは必ず承認確認を入れる）
4. **キャラクター人格** — 中立AIではなく「お母さん」という関係性を持つ（既存AIは無人格）
5. **画面外への能動的アクション介入** — チャット応答だけでなく、**実在のWebサイトをブラウザで操作して予約・注文・購入を完結**させる（既存AIは画面内の情報提供で完結）

これらはいずれも既存AIアシスタントの設計原則に**反する**選択であり、本サービスの差別化要因かつテーマ適合性の根拠である。

特に **(3) 判断機会の剥奪** と **(5) 画面外への能動的アクション介入** は本サービス独自の核心：
- Alexa：「Uber Eatsで頼みますか？」と必ず確認する／自前API以外は触らない
- ChatGPT：「次のアクションを実行してよろしいですか？」と確認する／チャット内で完結
- **わがママAI**：何も聞かずに **Amazon Nova Act が実サイトをブラウザ操作して予約・注文を完結**させる

「ユーザーが判断する瞬間」を**意図的に削除**し、かつ「アクションを画面の外（実Webサービス）まで貫通させる」ことで、ユーザーから判断機会＝学習機会を奪う。これが「人をダメにする」設計の中核メカニズムである。

### 2.3 ダメ度メトリクス（依存生成の評価軸）

ユーザーがどれだけ「ダメ」になったかを以下の3軸で**定量計測**し、ダッシュボードでユーザー本人に提示する。

| メトリクス | 定義 | 計測式 |
|---|---|---|
| 💖 **ママ溺愛度** | ユーザーが情緒的にママへ依存している度合い | 利用頻度 × 自発的会話量 × ありがとう率 |
| 🙏 **ママ任せ度** | ユーザーが判断・承認をスキップした割合 | 無承認実行回数 ÷ 総アクション数 |
| 👁 **ママ介入度** | ママが先回りでユーザー生活へ介入した頻度 | 能動通知数 ÷ 受動応答数 |

これらのメトリクスは：
- **設計指針**として機能する（各機能は3軸のいずれかを上昇させる方向で設計）
- **ユーザー体験の中核**となる（自分の「ダメ度」がスコアで見える）
- **デモ映え要素**として機能する（「ママ溺愛度97%！」が一目で伝わる）

### 2.4 倫理境界
- **架空のシナリオでの依存体験**を提供する（実害を与えない範囲に留める）
- 公序良俗に反する利用は禁止
- ユーザーは設定でいつでも依存度を調整できる（緊急時の解除手段を保証）

## 3. 既存AIとの差別化（Why not Alexa?）

「Alexaでよくないか？」への明確な回答。

### 3.1 機能比較表

| 軸 | Alexa/Siri/Google | ChatGPT/Claude | Replika/Character.ai | **わがママAI** |
|---|---|---|---|---|
| 起動方式 | 呼ばれて応答 | 聞かれて応答 | 話しかけて応答 | **先回りで勝手に介入** |
| キャラ性 | 中立・無人格 | 中立・無人格 | 友人・恋人 | **お母さん（愛＋圧＋干渉）** |
| 出力の深さ | 情報提供のみ | 情報提供のみ | 共感会話のみ | **意思決定＆実行まで代行** |
| データ統合 | 単発クエリ | チャット履歴 | 関係性メモリ | **スマホ全データ横断** |
| **画面外介入** | スマートホームAPIのみ | テキスト出力で完結 | テキスト出力で完結 | **🔥 Nova Actで実サイトをブラウザ操作（予約・注文・購入）** |
| 設計思想 | 役立つ | 賢くする | 寄り添う | **意図的にダメにする** |

### 3.2 なぜ既存AIには真似できないか

- **Big TechのAI**（Alexa, Siri, ChatGPT 等）は「ユーザーの依存を意図的に作る」設計を取れない。社会的責任・規制リスク・ブランド毀損のため。
- **キャラクター系AI**（Replika 等）は能動的介入機能を持たない。プライバシー観点・受動応答型のアーキテクチャのため。
- **タスクオートメーション系**（IFTTT, Zapier 等）は人格を持たないため、「お節介ママ」という心理的圧の伴う体験を提供できない。
- **Web自動化ツール**（Playwright 単体・Puppeteer 等）は能動性も人格も持たず、開発者向けツール止まり。

→ 「**人をダメにする思想 × ママ人格 × 能動介入 × 実行代行 × 画面外への貫通**」の5軸同時実装は本サービス独自。
→ 特に **画面外への貫通** は Amazon Nova Act（2025年GA）の登場で初めて実用域に入った領域であり、本サービスはこの最先端AWSサービスを「人をダメにする」目的のために再解釈する。

## 4. 機能要件

機能は **「ユーザーをどうダメにするか」** を評価軸として再設計し、独立性の高い4カテゴリ（=Unit分解の単位）で構成する。

### 4.1 機能カテゴリ

#### カテゴリA：思考代行（決定力を奪う）
ユーザーが「自分で決める」機会を奪い、選択疲れと判断力低下を引き起こす。
重要なのは **「完璧な提案」ではなく「ママらしい軽いお節介アドバイス」**。完璧すぎるとAIアシスタント感が出てしまうので、あえて押し付けがましいトーンを採用。

- **A1. 先回りコーディネートアドバイス**：朝、ユーザーが起きる前にママがチャットで「**今日は上着羽織っていきなさいよ、肌寒いから**」と通知。簡易な画像（イラスト的なコーデ案）を生成して添える
- **A2. 先回り食事アドバイス**：「**最近野菜足りてないわよ、ランチはサラダ多めにしなさい**」と昼前に通知
- **A3. 意思決定相談（汎用）**：人生の判断（買う/買わない、行く/行かない）をママに丸投げできる

#### カテゴリB：実行代行（行動力を奪う）
ユーザーが「自分で動く」機会を奪い、行動力と社会対応力を低下させる。
本カテゴリは **Amazon Nova Act**（ブラウザ操作AIエージェント、2025年GA）を核として、**実在するWebサービスをママが代わりに操作**する。これにより「個人開発者は予約APIにアクセスできない」という外部制約を物理的に回避し、ユーザーから「自分で操作する機会」を完全に奪う。

- **B1. 代理ブラウザ操作（予約・注文・購入）**：Nova Actで食べログ/ホットペッパー/Uber Eats Web/Amazon等を実際に操作。「ママが店予約しといたよ」「ママがUberで頼んどいたよ」「ママが洗剤買っといたよ」を実現
- **B2. 代理コミュニケーション**：友人への返信・連絡・催促をママが代筆・代行
- **B3. 画面外への通知連動**：Google Calendar API でユーザーカレンダーに予約自動登録、SES で予約確定メール風通知を発信

#### カテゴリC：先回り介入（自己管理力を奪う）
ユーザーが「自分で管理する」機会を奪い、自律的な生活管理能力を低下させる。

- **C1. 就寝催促**：深夜のスマホ使用を検知し、強制的に画面を暗くする / 「もう寝なさい！」
- **C2. 帰宅促進**：夜遅い外出を検知し「早く帰りなさい」と圧をかける
- **C3. 支出監視**：使いすぎを検知し「今月使いすぎ！」と警告→自動で節約モード起動
- **C4. 締め切り催促**：締め切りが近づくと「ちゃんとやってる？」と定期的に進捗を催促

#### カテゴリD：人格・関係性・計測（依存を深める）
ユーザーが「ママ」という関係性に情緒的に依存する状態を作り、その依存度を可視化する。

- **D1. ママ人格チャットUI**：LINE風UIでママ人格（口調・距離感・お節介度）で会話
- **D2. スマホデータ統合**：カレンダー・購買・位置・健康データを横断的に把握
- **D3. ママ溺愛度ダッシュボード**：§2.3 のメトリクス3軸（ママ溺愛度／ママ任せ度／ママ介入度）をリアルタイム可視化。ユーザーは自分のダメ度をエンタメ的に確認できる
- **D4. 継続学習**：ユーザーの行動・好みを学習し、より「ダメにする」精度を上げる

### 4.2 MVPスコープ（5/30 予選デモ向け）

#### デモコンセプト：**「おはよう、もう全部終わってるよ」**

ユーザーが朝起きると、ママがすでに全部やり終えている世界観。
- 👕 服のアドバイスがチャットに届いている（簡易画像付き）
- 🍱 ランチの方針も「サラダにしな」と決まっている
- 💬 友達への返信が**既読まで完了**している
- 💖 そして**ママ溺愛度98%**のゲージが上がっている

→ ユーザーは何も決めてない、何も実行してない、なのに1日が回ってる。
→ **「人がダメになる瞬間」を1画面で体験**できるデモ。

#### MVP機能セット（6機能）

| # | 機能 | カテゴリ | デモでの役割 | 主に体現する設計選択 |
|---|---|---|---|---|
| **F1** | ママ人格チャットUI | D1 | 全シーンの土台。LINE風 + ママ口調 | (4) キャラクター人格 |
| **F2** | ママの先回りアドバイス（コーディネート＋食事、テキスト＋簡易画像生成） | A1+A2 | 「上着羽織りな」「サラダにしな」を画像付きで | (1) 能動的介入 |
| **F3** 🔥 | **ママの代理ブラウザ操作（予約・注文）** — Nova Actが食べログ/Uber Eats Web等を実際に操作して予約・注文を完了 | **B1** | **「ママが昨晩のうちに店予約しといたよ」「ママがUberで頼んどいたよ」が実現** | **(2) 実行代行 + (3) 判断機会の剥奪 + (5) 画面外への介入** |
| **F4** | ゼロタップ代理返信 | B2 | 友達への返信が**既読まで完了** | (2) 実行代行 + (3) 判断機会の剥奪 |
| **F5** | 💖 ママ溺愛度ダッシュボード | D3 | 3軸メトリクスでダメ度を可視化、デモのフィナーレ | 評価軸の可視化 |
| **F6** | スマホデータ統合（カレンダー・天気） | D2 | F2/F3を成立させる基盤 + Google Calendar API でユーザーのカレンダーに予約を勝手に登録 | 基盤 |

→ **5つの設計選択 (1)〜(5) のすべてが MVP でカバーされる構成**。
→ F3 が本サービスの **核**：個人開発者が予約APIアクセスできない問題を Nova Act が物理解決し、「人をダメにする」体験の濃度が桁違いに上がる。

### 4.3 Out of Scope（明示的に「やらない」）

ハッカソン期間内では**意図的に実装しない**項目を明示する。MVP の集中度を上げるため、また実現可能性が低い項目を要件レベルで切り離すため。

| 機能 | 「やらない」理由 |
|---|---|
| A3. 意思決定相談（汎用） | F2/F3の方が「ゼロタップ」演出が強いため、汎用判断はMVP外 |
| 公式予約・注文API連携（Uber Eats Marketplace API、ぐるなびAPI 等） | 個人開発者は契約・NDAアクセスが困難。**Nova Actのブラウザ操作で代替**するため不要 |
| 音声インタラクション全般（電話発信・音声対話） | Amazon Connect・Polly・Lex 系は今回採用しない。世界観はテキスト＋画像＋ブラウザ操作で構成 |
| スマート家電（実機連携） | デモ環境構築コストが見合わない |
| C1. 就寝催促 | デモは朝のシーンに集中する方針のため、夜系機能はカット |
| C2 帰宅促進 / C3 支出監視 / C4 締切催促 | カテゴリC はすべて MVP外、今後の展望 |
| プレゼント選定・発注 | 友人データ取得・同意フローが整備困難 |
| 起床サポート（ネイティブアラーム連携） | OS制約が強く、デモ映えしない |
| 美容院・身だしなみ管理 | 外部API連携が複雑 |
| D4. 完全自動学習（ML基盤） | 機械学習基盤の構築コストが見合わない。ルールベース＋LLMで代替 |

## 5. 非機能要件

### 5.1 フロントエンド
- スマホアプリ（iOS / Android）または PWA
- 実装方針: **React Native + Expo** を想定（クロスプラットフォーム対応・実装速度優先）
- ネイティブアラーム・プッシュ通知連携可能なこと

### 5.2 バックエンド（ハイブリッド言語構成）

本サービスは Nova Act SDK が Python のみ提供という制約を受け入れ、**「Nova Act 実行層だけを Python に隔離し、それ以外を TypeScript で統一する」** ハイブリッド構成を採用する。

#### 5.2.1 メインバックエンド（TypeScript 統一層）
- 言語: **TypeScript / Node.js**
- フレームワーク: **Hono**
- AI推論（テキスト）: **AWS Bedrock**（Claude 系列、ママ口調生成・行動判断）
- AI推論（画像）: **AWS Bedrock**（Titan Image Generator または Stable Diffusion XL、F2 のコーデ画像）
- 実行基盤: AWS Lambda + API Gateway
- 定期処理: EventBridge Scheduler（朝の先回り通知等）
- データ: DynamoDB（状態・ダメ度メトリクス管理）+ S3（生成画像）
- 外部 API: Google Calendar API（OAuth2、予約をユーザーカレンダーに自動登録）、ホットペッパーAPI（店検索、無料）、天気API
- カバー範囲: F1, F2, F4, F5, F6 のすべて、および F3 の TypeScript 側呼び出し処理

#### 5.2.2 Nova Act 実行層（Python 隔離層）
- 言語: **Python**（Nova Act SDK 制約のため）
- ライブラリ: `nova-act` SDK
- 実行基盤: **AWS Lambda（コンテナイメージ）** — ブラウザバイナリ込みのため
- カバー範囲: F3 のブラウザ操作ワークフローのみ
- 隔離方針: 1つの Python Lambda に Nova Act 関連コードを集約し、TypeScript 層からは「予約・注文を実行する黒箱」として扱う

#### 5.2.3 言語境界の連携方式
- **MVP（5/30 予選向け）**: TypeScript Lambda から **AWS SDK Lambda.Invoke** で Python Lambda をクロスリージョン直接呼び出し（最もシンプル、最速で実装可能）
- **決勝拡張（6/26 向け、余裕があれば）**: **Amazon Bedrock AgentCore Runtime** 経由に移行
  - 長時間ブラウザセッション維持
  - 管理ブラウザの再利用によるコールドスタート回避
  - 最新AWSサービス活用としてのアピール強化
- 言語境界は明確な API 契約（JSON in / JSON out）で疎結合に保つ

### 5.3 インフラ（マルチリージョン構成）

| リージョン | 役割 | 含まれるリソース |
|---|---|---|
| **`ap-northeast-1`（東京）** | メインリージョン | TypeScript Lambda（Hono）、API Gateway、Bedrock（テキスト・画像）、DynamoDB、S3、EventBridge Scheduler、SES |
| **`us-east-1`（バージニア北部）** | Nova Act 専用 | Python Lambda（nova-act SDK・コンテナイメージ）／決勝拡張時は Bedrock AgentCore Runtime + Browser |

- Nova Act が `us-east-1` のみサポートのため、マルチリージョン構成は不可避
- リージョン間連携: TypeScript Lambda → Python Lambda の **クロスリージョン Lambda Invoke**（IAM ポリシーで明示許可）
- IaC: **AWS CDK（TypeScript）** — 1つの CDK プロジェクトで両リージョンのスタックを管理

### 5.4 セキュリティ
- Security Baseline Extension 適用（全SECURITYルールをブロッキング制約として適用）
- スマホデータへのアクセスには適切な権限管理・暗号化
- ユーザー同意フローを設置（PII 取扱い）

### 5.5 テスト
- Property-Based Testing (PBT) Extension 適用
- 適用範囲: **純ロジック層は PBT 必須**、LLM出力・外部I/O層は example-based testing で代替

### 5.6 拡張性・モジュール性（Unit分解）
- 機能カテゴリ A/B/C/D は **独立した Unit** として設計し、個別に差し替え・追加可能とする
- 外部API連携（モック含む）は疎結合に保つ
- ママ人格（D1）の口調・距離感はパラメータで調整可能

### 5.7 通知ポリシー
- ママ人格のため**意図的に多めの通知**を許容（「うるさいママ」が世界観の一部）
- 静音時間帯（深夜のC1除く）はユーザー設定で調整可能
- 緊急停止（依存度ゼロ化）の手段を提供

## 6. 今後の展望（ハッカソンスコープ外）
